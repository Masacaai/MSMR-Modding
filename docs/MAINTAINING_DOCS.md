# Maintaining this repository: where things go

Read this before you add, move or edit documentation, tools or shared code. It is the structure the repository is held to; if a change
does not fit it, either change the change or change this file in the same commit and say why. (Agents: [AGENTS.md](../AGENTS.md) points here.)

The repository has two jobs: **documentation for the mods**, and an ever-growing **reference for how Spider-Man Remastered works inside**
(the "decomp bible"). They live in separate places so each stays easy to navigate.

## The map

```
README.md                  what the mods are; links onward. Mod-first.
AGENTS.md, CONTRIBUTING.md rules for agents / people. THIRD_PARTY_NOTICES.md credits and licenses.

<Mod>/                     EndlessArena, ManhattanSkies, EchoesOfTime, DisableWebs: ONLY what is specific to that mod
  README.md                what it does, how to use it, layout of its folder
  mod.json                 package name, file name and version (read by common/build/pack.ps1)
  build.cmd                short: includes common/, compiles src/, calls common/build/finish.cmd
  src/                     the mod's own code
  docs/                    design, ledger, bugs, how-tos, ROADMAP.md, releases/ (release notes)
  data/, tests/, tools/    only if this mod alone uses them

common/                    code shared by 2+ mods: ONE copy, never forked
  (log, memory, scan, gamethread, watchpoint)   engine layer
  game/                    game access used by several mods: natives, entity, spawn, psinput
  modmenu/                 the Settings-tab library
  build/                   setup.cmd, finish.cmd, pack.ps1: toolchain, packing, Mods Library copy
vcpkg.json                 the one dependency manifest (MinHook); output vcpkg_installed/ is git-ignored

docs/                      repository-wide guides: GETTING_STARTED, REVERSE_ENGINEERING (method), RELEASING, ROADMAP, this file
docs/internals/            THE BIBLE: what is known about the game, organized by SYSTEM (README.md is the index)
recon/                     generated reference dumps of the game (types, enums, events, ...): data, not prose; README.md says how each is made
tools/                     every reusable script/program, by purpose (sigtools, assets, memory, roster, toctool, runviewer, docs, wiki, github)
notes/                     LOCAL ONLY, git-ignored: session logs, request lists, play-test checklists, drafts
```

## Where does this go?

| You have... | Put it in |
|---|---|
| A fact about how the game works (an address, a struct layout, a function's contract, how a system behaves) | **`docs/internals/<system>.md`**, with a confidence tag, even if you found it for one mod |
| How a mod uses that fact | The mod's `docs/` or a code comment that **links to** the internals page. Do not copy the fact |
| A design decision or backlog item for one mod | `<Mod>/docs/` (LEDGER, ROADMAP, BUGS) |
| An idea that spans several mods | `docs/ROADMAP.md` |
| Code two or more mods need | `common/` (move it there the second time it is needed; do not copy) |
| A script that reads game files or dumps | `tools/<purpose>/`, not inside a mod folder. A script that only makes sense for one mod's data may stay in that mod's `tools/` |
| A dump regenerated by a tool | `recon/`, and say in `recon/README.md` which tool makes it |
| Extracted game bytes (textures, `.actor`, `.config`, memory dumps, saves) | **Nowhere in git.** Facts go in docs; bytes stay local and ignored |
| Release notes for a version | `<Mod>/docs/releases/` |
| A session log, a wish list for another agent, a play-test checklist, a "what happened today" story, a draft | **`notes/`** (local). See below |

## Rule: session-specific material is local-only

Back-and-forth between a maintainer and an agent, per-session logs, "answers to the requests of date X", test checklists for a build that has not
been played, and chronologies of who found what when are working notes. Keep them in `notes/` (git-ignored). The repository holds the
**distilled, durable result**:

- State what is true, not how the conversation went. "`HeroAbilityLock` is a component at +0x.. [verified]", not "in session 3 we tried...".
- Date a *finding* (`2026-11-19`) so people can judge its age; do not narrate the session around it.
- A finding in a mod's notes that is about the game belongs on an internals page (rewrite it there as a statement of fact, then link from the mod doc).
- A one-off oddity is a record in the mod's `BUGS.md`; a recurring one is an issue. A play-test checklist is not either: it stays in `notes/`.
- Do not name the agents or models that did the work in repository docs. The fact is what matters.

Pages that are chronological by nature (`ui-recordings.md`, `atmosphere-and-menu-recon-log.md`) are legacy: when you touch one, move what you
changed into the topic pages and shrink the log; do not add new "Part N" or "session N" sections.

## Writing `docs/internals/` pages

- One page per **system** (spawning, UI, input, lighting...), named in lower-kebab-case after the system, not after a mod, a date or a person.
  If a page passes about 600 lines or covers two systems, split it and update the index.
- Start with `# Title` and a short paragraph saying what the page covers and the build (4.0630.0.0). Use `##` for sections: they appear in the generated index and wiki sidebar.
- Tag claims: `[verified]` tested in game, `[RE]` read from disassembly, `[I]` inferred, `[?]` unknown. Never invent an address or offset; write `unknown`.
- Say how it was found (a tool command, a log line, a function address) so the next person can re-check it when the game updates.
- Addresses are `exe+RVA` for `Spider-Man.exe` 4.0630.0.0. No leaked Insomniac material (see [REVERSE_ENGINEERING.md](REVERSE_ENGINEERING.md)).
- Link, do not repeat: cross-link pages (`[spawning](internals/entities-and-spawning.md#...)`), and link from code comments to the page that explains the code.
- Dumps that a tool can regenerate go in `recon/`; the page explains how to read them.

After adding, renaming or splitting a page or a `##` heading:

```
python tools/docs/gen_internals_index.py     refresh docs/internals/README.md's generated index
python tools/docs/check_links.py             every relative link and #anchor in every .md must resolve
python tools/wiki/sync.py                    optional: build wiki-out/ and look at it
```

If you move or rename files, use `git mv`, list the old -> new paths in a JSON file and run `python tools/docs/rewrite_links.py <file.json>` to repair links, then grep
the source comments (`git grep -n "docs/"`) for stale paths. Code comments that cite docs use the repository path (`docs/internals/ui.md`).

## The wiki

The GitHub Wiki is a **generated, read-only mirror** of `docs/internals/` and two guides (Getting started, the reverse-engineering method), for browsing and search.
`.github/workflows/wiki.yml` rebuilds it when those sources change on `main` (`python tools/wiki/sync.py --push` does the same by hand). Never edit the wiki directly:
the next sync overwrites it. Mod documentation stays in the repository (it changes with the code and must be reviewed with it). One-time setup: enable the Wiki in the
repository settings and save any first page; the workflow takes over.

## Shared code and the build

- A mod's `build.cmd` is short: `call common\build\setup.cmd`, one `cl` line (include `common`, `common\game`, `common\modmenu` as needed; compile `src\*.cpp` plus the shared sources it uses), `call common\build\finish.cmd`.
- Version and package name live in the mod's `mod.json`. The author is the same for every mod (AGENTS.md rule 10). Do not add per-mod `pack.ps1` files.
- Every build leaves the packed `.script` in Overstrike's Mods Library (`finish.cmd`); installing into the game is done by the user through Overstrike. Never write the game's `scripts\` folder.
- Code that two mods both need moves into `common/` in the same commit that adds the second user; update `common/README.md`. Mod-specific code stays out of `common/`.
- `common/gamethread.cpp` needs each mod to supply a `natives.h` with `natives::GameThreadTick`: mods that include `common/game/` get the shared one; a mod with its own small list (Manhattan Skies) keeps its own `src/natives.h`. Never put both on one include path.

## Adding a mod

1. `<Mod>/` with `README.md`, `mod.json`, `build.cmd` (copy a sibling), `src/`, `docs/` (and `docs/releases/`). A mod that is not ready for release stays out of git: add its folder to `.git/info/exclude` (local to your clone), **not** to `.gitignore`, so its name is not published. Its name appears in no tracked file until release.
2. Add it to the table in the root `README.md` and to `docs/README.md`.
3. Put anything you learn about the game on the internals pages, not in the mod's docs.

## Checklist before you commit

- [ ] No game material, no memory dumps, no saves; nothing from `notes/` or other ignored folders staged (`git status`).
- [ ] Every fact you added about the game is on an internals page with a tag; the mod docs link to it.
- [ ] `python tools/docs/gen_internals_index.py` and `python tools/docs/check_links.py` are clean.
- [ ] Code comments that cite docs point at paths that exist.
- [ ] Nothing session-specific (conversation dates, who-asked-what, test checklists) is in a tracked file.
- [ ] The README of every folder you changed still describes the folder.
